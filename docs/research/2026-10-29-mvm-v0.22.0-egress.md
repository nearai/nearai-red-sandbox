# mvm v0.22.0 egress: how it works on HVF, and what enabling it changes

Source: tinylabscom/mvm at tag `v0.22.0`. All paths below are repo-relative and all line numbers are at that tag, unless a line says otherwise. Local copies are under `scratchpad/mvmsrc/`. The work was read-only: no machine was created, started or modified. `mvmctl --help` output was read from `~/.local/mvm/v0.22.0/mvmctl`.

## TL;DR

- Neither `--net` nor `--allow-host` gives unrestricted egress. `--net` turns on the built-in `dev` allowlist: npm, crates.io, PyPI, github.com, api.github.com, api.openai.com and api.anthropic.com, all on port 443. `--allow-host` replaces that list with your own. The unrestricted preset can't be reached from these flags.
- The guest has no NIC. Apps reach the network through a loopback SOCKS5/HTTP proxy at `127.0.0.1:1080` and a DNS stub at `127.0.0.1:53`, both run by `mvm-egress-client` inside the guest. That client speaks authenticated FlowMux over vsock port 5253. On the host, the HVF supervisor relays that traffic to a per-VM `mvm-network-endpoint` process over a UDS. That process is the only place an allow/deny decision is made.
- Enforcement is by host-pinned IP and port. The host resolves each allowlisted name once, when the endpoint starts, and admits TCP only to those IPs on the listed ports. There is no SNI or Host check on opaque flows, so any other virtual host served from the same pinned IPs can be reached (CDN co-tenancy, domain fronting).
- No TLS interception by default. TLS is only terminated for hosts with a bound `--secret`, or for routes with `intercept = true` / `--allow-endpoint`. In those cases a per-VM name-constrained CA is created and the guest env is pointed at a combined bundle.
- Biggest change to the risk picture: **on macOS, `mvm-network-endpoint` runs with no sandbox** (Landlock and seccomp are Linux-only). It parses hostile guest bytes with your user's privileges. With egress off it isn't started at all.
- Connection-rate limiters are disabled by default (set to 0). There are no byte or bandwidth caps. The only limits are concurrency ceilings: 4096 TCP flows, 256 UDP associations, 1024 DNS bindings, 16 sessions.
- An allowlist admits no UDP. DNS is answered only from the pins, so DNS tunnelling is closed. ICMP is a mediated echo to allowlisted hosts only.
- Logging: every allow and deny is written as a signed JSONL envelope to `~/.mvm/audit/<tenant>.jsonl` (`local.jsonl` by default), tagged with `labels.vm_name`. The launcher can tail and filter that file. There is no `mvmctl vm egress-denials` verb; the CLI surface is `mvmctl explain` and live stderr on foreground runs.
- The policy is fixed for each boot. `machine reconfigure --net/--no-net/--allow-host/--clear-allow-host` stops and restarts the VM. `--peer`, `--grants-file` and `--policy` are only taken at create or start time.

## 1. End-to-end path on HVF

### Turning flags into a policy

`crates/mvm-client/src/admission/run_network.rs:92-104`:
```rust
let base = if !allow_host.is_empty() {
    ... NetworkPolicy::allow_list(rules)
} else if let Some(preset) = preset {
    NetworkPolicy::preset(preset)
} else if net {
    NetworkPolicy::preset(NetworkPreset::Dev)
} else {
    NetworkPolicy::deny_all()
};
```
- If `--allow-host` is given, `--net` is ignored (narrowest wins). A tested invariant says `--net` is never unrestricted (`run_network.rs:186-190`).
- The `dev` preset is defined in `crates/mvm-contract/src/policy/network_policy.rs:617-635`: `registry.npmjs.org`, `crates.io`, `static.crates.io`, `index.crates.io`, `pypi.org`, `files.pythonhosted.org`, `github.com`, `api.github.com`, `api.openai.com` and `api.anthropic.com`, all on port 443.
- The help text for `machine reconfigure --net` says "broad egress + DNS" (`crates/mvm-cli/src/commands/machine/mod.rs:957`). That is out of date; it is the same `dev` allowlist.
- `--allow-host` parsing is in `run_network.rs:153-170`. It splits `HOST[:PORT]` at the last `:`. A bare host means port 443. Port 22 is refused. There are no wildcards and no CIDRs on this flag: the host is either a DNS name or a literal IP. A wildcard such as `*.suffix` is only accepted in manifest `[[network.routes]]`, and it only narrows destinations some other grant has already admitted (`docs network-egress-policy.mdx:95`).
- `--peer NAME:PORT=ADDR:PORT` (`run_network.rs:122-148`, `crates/mvm-contract/src/peer.rs:193-201`) adds a route for `<name>.mvm.peer:PORT`. The target must be a literal IP and nothing else is checked, so it can be `127.0.0.1` or any other address. The gate's `decide_peer` (`egress_gate.rs:412-445`) does **not** run the restricted-address classifier. **`--peer` is the operator's way to give the guest a host-loopback port; never pass it.** A side note: on HVF, a policy with only peers won't even start the endpoint, because `hvf_endpoint_needed` checks `allows_egress()` rather than `admits_outbound()` (`crates/mvm-backends/src/driver/hvf_process.rs:193-199`).
- `--grants-file` is a JSON `Grants` document. Its `egress` part is `{"allow":[{"host":..,"port":..}]}` (`crates/mvm-contract/src/grants/mod.rs:69-71`). Layers are folded per dimension in the order CLI > grants file > manifest > **host config `default_grants()`** (`crates/mvm-client/src/admission/run_grants.rs:80-101`). An egress grant found in any layer becomes the policy (`run_grants.rs:194-215`). **Check that your host config has no default egress grant.** Otherwise a machine created with no flags could still get egress from it.
- `--policy NAME|PATH` applies authored profiles. They only narrow: `narrow_egress_with_policy` drops entries a profile blocks or denies (`run_grants.rs:133-160`). The built-in groups are `github`, `llm-apis`, `registries` and `offline` (`crates/mvm-client/src/policy_profiles/builtin/groups/*.toml`).

### Guest side (nothing for you to install)
- `crates/mvm-build/src/oci_runtime_inject.rs:1-28, 160-161` copies `mvm-guest-agent`, `mvm-guest-netinit`, `mvm-egress-client` and an entrypoint runner into any OCI rootfs (the lean path uses the `/mvm/runtime` overlay instead).
- `crates/mvm-core/src/guest_netd.rs:17,31,33`: the proxy listens on `127.0.0.1:1080`, the DNS stub on `127.0.0.1:53`, and the ICMP mediator on `127.0.0.1:1081`. Workload env comes from `proxy_env_vars` (`guest_netd.rs:102-123`): `HTTP_PROXY` and `HTTPS_PROXY` set to `http://127.0.0.1:1080`, `ALL_PROXY` set to `socks5h://127.0.0.1:1080`, and `NO_PROXY=localhost,127.0.0.1,::1`. This env is only added when the per-VM egress marker exists (`crates/mvm-hostd/src/workload_env.rs:28-33`). `/etc/resolv.conf` is bind-mounted to the loopback stub (`crates/mvm-agentd/src/guest_net.rs:151-156, 405-437`).
- `crates/mvm-agentd/src/flowmux_egress.rs:1-10, 95-110`: one authenticated, reconnecting FlowMux session carries SOCKS5 CONNECT, HTTP CONNECT, absolute-form HTTP forwarding, SOCKS5 UDP ASSOCIATE, and the DNS stub's `Resolve` frames.

### Transport
- The guest connects over AF_VSOCK to CID 2, port 5253 (`docs guides/networking.md:105-119`). On HVF, the supervisor's in-process vsock device relays that port to `egress_relay_socket`, a UDS (`crates/mvm-backends/src/driver/hvf.rs:160-185`, `crates/mvm-hostd/src/bin/mvm-hvf-supervisor.rs:390-406`). The endpoint binds that UDS (`crates/mvm-hostd/src/bin/mvm-network-endpoint.rs:597-610`). FlowMux frames are capped at 64 KiB of payload (`crates/mvm-contract/src/protocol/network_flow/limits.rs`). The session is authenticated with a per-boot Ed25519 identity delivered on a drive (`mvm-network-endpoint.rs:952-962`).
- With a deny-all policy and no secrets, **no endpoint is spawned** and `EGRESS_PORT` stays unwired (`hvf_process.rs:186-199`). That is your current posture.

### Host side: where the allowlist is enforced
- `crates/mvm-hostd/src/supervisor/network_endpoint.rs:46-57` builds the gate once, when the endpoint starts:
```rust
let pins = mvm_core::policy::dns_pin::resolve_network_policy_pins(policy);
let now = chrono::Utc::now().to_rfc3339();
EgressGate::from_network_policy(policy, &pins, &now).with_peers(policy.peers().to_vec())
```
- `crates/mvm-core/src/policy/dns_pin.rs:47-68`: **the host resolves each name once, using the host's own resolver** (`to_socket_addrs`), and pins the result with a 24 h TTL. A literal IP pins to itself.
- `crates/mvm-contract/src/policy/projection.rs:289-330`: pins become `CanonicalRule{proto: Tcp, net: <pinned ip>/32|128, port}`. If any one host has no pin, an expired pin, or an empty pin, **the whole gate becomes deny-all** (`egress_gate.rs:310-332`). One allowlisted name that fails to resolve at boot therefore turns off egress entirely. Expiry is only checked at build time, so a machine running longer than 24 h keeps using its boot-time IPs.
- `crates/mvm-hostd/src/supervisor/flowmux/open_flow.rs:141-210` handles `OpenTcp`: parse `host:port`, check the rate limit, then `gate.decide_target`.
- `crates/mvm-vmm/src/vsock_egress_bridge/egress_gate.rs`:
  - `decide_hostname_request` (641-705): if the name is pinned, use only the pinned IPs. On a non-unrestricted gate an unpinned name is refused **without any lookup**.
  - `decide_addr_for_proto` (594-619): an IP literal is allowed if it is in the pinned rule set on that port.
  - `restriction` (580-592) and `restricted_address.rs`: metadata (169.254.169.254 and others), loopback, unspecified, link-local and CGNAT 100.64/10 are refused **whatever the policy says**. Private ranges (RFC1918, ULA), multicast and reserved addresses are refused unless a rule names that IP. One subtle way that happens: an allowlisted hostname that resolved to a private IP at admission. IPv4-mapped, NAT64, 6to4 and Teredo addresses are judged by the IPv4 address inside them (`docs network-egress-policy.mdx:135-163`).
  - `dns_verdict` (711-744): names are answered from the pins only. Unpinned names get REFUSED. Only an unrestricted gate does live lookups, and those are filtered for rebinding.
  - TCP/22 is always refused (`network_policy.rs:84-91`, `run_network.rs:164-168`).

### Bypass analysis
| Attempt | Result |
|---|---|
| Different SNI or Host header to an allowed host's IP | **Allowed.** Opaque flows are spliced byte for byte. There is no SNI or Host inspection unless the destination is terminated (`classify.rs:91-104`; grepping hostd and vmm for SNI only finds leaf minting). Any vhost on the pinned IPs can be reached, which matters for CDN-fronted APIs. |
| IP literal | Allowed only if it is in the pinned set and the port matches. Otherwise denied with `AddressNotAdmitted` or `RestrictedAddress`. |
| DNS rebinding | Not possible. Resolution happens once on the host, the guest never resolves, and the guest's DNS answers come from the pins. |
| Host loopback, 169.254.x, metadata | Always refused, with no override, except through an operator-supplied `--peer`. |
| Host LAN (192.168.x and so on) | Refused unless named, or unless an allowlisted name resolved there on the host (split-horizon or VPN DNS). |
| Other VMs | Only reachable through `--peer`, or through `--port` ingress listeners that you declare. |
| Raw sockets or non-proxy apps | No path at all: no NIC, routes go only to lo. |
| Talking FlowMux directly (a hostile guest root reading the identity drive) | Gets the same host-side gate, so nothing is widened. |

The host's own outbound proxy env is passed to the endpoint's forward leg as `proxy_https`, `proxy_http` and `no_proxy` (`crates/mvm-vmm/src/host/network_endpoint_spawn.rs:955-971`). If the host has `HTTPS_PROXY` set, allowed traffic leaves through that proxy.

## 2. TLS and `egress_ca`

`crates/mvm-core/src/crypto/egress_ca.rs:1-29`:
> Transparent `https` substitution terminates TLS at the host for **bound hosts only** ... each VM gets a freshly-minted CA whose X.509 `nameConstraints permitted` is exactly the plan's bound hosts ... It is still **not** the egress control.

- When a flow is terminated: `crates/mvm-hostd/src/supervisor/network_endpoint_proxy/classify.rs:91-104`. It requires a bound secret (`--secret`) or a route that grants interception (`intercept = true` or `--allow-endpoint`), plus a per-VM CA. Termination happens only on port 443 (TLS) or port 80 (cleartext).
- **With plain `--allow-host` or `--net`, nothing is terminated.** curl in the guest does end-to-end TLS through `socks5h` or HTTP CONNECT and needs no extra CA.
- When a CA does exist, the host env sets `SSL_CERT_FILE`, `CURL_CA_BUNDLE` and `REQUESTS_CA_BUNDLE` to `/run/mvm/ca-bundle.crt`, and `NODE_EXTRA_CA_CERTS` to `/run/mvm/egress-ca.crt` (`crates/mvm-hostd/src/workload_env.rs:41-67`). The guest builds that bundle from the baked roots (`/etc/ssl/certs/ca-certificates.crt`, `/etc/ssl/cert.pem`, `/etc/ssl/certs/ca-bundle.crt`) plus the per-VM certificate (`crates/mvm-agentd/src/flowmux_drive.rs:63-100`). The CA key stays on the host (`network_endpoint_spawn.rs:117-140`). It is persisted in the VM state dir as `egress-ca.json`, owner-only.
- curl notes:
  - `HTTPS_PROXY=http://127.0.0.1:1080` takes priority over `ALL_PROXY` for https URLs, and curl uses CONNECT there, which works.
  - BusyBox `wget` sends HTTPS through the HTTP proxy in absolute-URI form, which the proxy refuses (issue #3929). Use curl or Python on Alpine.
  - A curl call that skips the env (`--noproxy '*'`, or a tool that ignores proxy env) has no path out.

## 3. Logging and observability

- Every decision goes to the chain-signed audit log `~/.mvm/audit/<tenant>.jsonl` (`crates/mvm-hostd/src/audit/emitter.rs:247-256`). The default tenant is `local`; on this host that file is `~/.mvm/audit/local.jsonl` and it has rotated segments `local.seg-*.jsonl`.
- Each line is a `SignedEnvelope{entry, canonical, prev_hash, signature}`. The fields are base64url, and `signature` is Ed25519 over `bytes || prev_hash` (`crates/mvm-contract/src/verify.rs:54-101`, `crates/mvm-hostd/src/supervisor/audit_file.rs:1-35`). `entry` holds `timestamp`, `tenant`, `plan_id`, `event` and `labels`.
- Egress events:
  - `host.flow.allowed`, with labels `stream_id`, `class`, `route`, `target`, `resolved_ips` and, when terminated, `termination` (`open_flow.rs:228-237, 320-334`).
  - `host.flow.denied`, with `target`, `class` and `reason`. The reason is `policy_denied`, a restricted class such as `cloud_metadata`, `loopback` or `private_range`, `rate_limited`, `resource_exhausted`, `connect_failed`, `typed_transform_required` or `endpoint_rules_unenforceable`.
  - `dns.resolved` / `dns.refused`, with `qname`, `qtype` and `resolved_ips` (`crates/mvm-hostd/src/supervisor/flowmux.rs:699-755`).
  - `host.route.decided` and `icmp.refused`. AI metering adds `host.ai.usage`.
  - Payload bytes are never logged. A payload log module, `supervisor/network/flow_byte_log.rs`, does exist (per-VM, 0600, plaintext). But GitHub code search on the default branch, and a grep of the v0.22.0 FlowMux, endpoint and proxy files, find no caller of `FlowByteLogWriter` outside its own module. It doesn't appear to be wired.
- Per-machine filtering: `entry.labels.vm_name` (`LABEL_VM_NAME = "vm_name"`, `crates/mvm-hostd/src/supervisor/audit_recorder.rs:376`). The CLI filters the same way (`crates/mvm-cli/src/commands/vm/egress_denials/denial.rs:96-140`). Several machines share one tenant chain. Verify the chain with `mvmctl trust audit verify`.
- CLI surface:
  - `mvmctl explain <run_id|machine> [--json] [--review]`.
  - Live `[mvm] egress blocked:` lines on stderr for foreground runs and for `machine logs -f`.
  - `mvmctl run --json` gives `egress_denials[]`.
  - The `egress_denials` module is internal; there is no `vm egress-denials` subcommand in v0.22.0. `mvmctl vm` is not a command in this build, as the help output confirms.
- The recorder is `Option` (`flowmux.rs:412-425`). Check that the endpoint records on your setup by looking for `host.flow.*` lines after a test run.
- Your launcher can tail `~/.mvm/audit/local.jsonl` and filter with `jq 'select(.entry.labels.vm_name=="<name>" and (.entry.event|test("^host\\.flow|^dns\\.|^icmp\\.|^host\\.route")))'`.

## 4. Guest requirements

- Nothing extra is needed in the image; mvm injects the runtime into any OCI rootfs (`oci_runtime_inject.rs`). No kernel change or route setup is needed: the guest stays on lo only.
- It is transparent to the image but **not** to the application. Only proxy-aware clients, or anything going through `getaddrinfo` plus a SOCKS or HTTP proxy, get out. That covers curl, pip, npm, git-over-https and Python `urllib`. Static binaries that ignore `*_PROXY`, `ping` (use the mediated helper under `/run/mvm/bin`), and arbitrary UDP don't.
- The mvm docs say raw ICMP and non-proxy sockets are "intentionally not available" (`docs guides/networking.md:40-42`).

## 5. Limits

- `crates/mvm-hostd/src/supervisor/flowmux/registry.rs:115-131`, the defaults:
```rust
max_tcp: 4096, max_udp: 256, max_dns: 256, max_http: 256, max_icmp: 64,
initial_credit: 64 * 1024, udp_idle_timeout: 60s, max_udp_peers: 16,
tcp_connect_rate: 0, udp_open_rate: 0, dns_resolve_rate: 0, icmp_echo_rate: 0,
```
  `from_network_limits` (`registry.rs:139-150`) only overrides the counts, from the signed `NetworkLimits` (defaults 4096 TCP, 256 UDP, 1024 DNS bindings, 16 ingress; `crates/mvm-contract/src/plan/types.rs:74-99`). **Per-second connect and resolve limiting is off in production.** Only tests set a non-zero rate.
- `crates/mvm-hostd/src/supervisor/egress_rate.rs:26-30`: 100 requests/s, 32 in flight, 32 tunnels. It is only wired to ICMP (`resources.rs:31,55`; `flowmux.rs:114,1048`). The module comment says raw TCP tunnels use it, but in v0.22.0 the FlowMux TCP path does not. `try_admit_tunnel` has no callers outside `egress_rate.rs`; I checked with code search and with greps of the v0.22.0 hostd files.
- `crates/mvm-hostd/src/supervisor/flowmux/resources.rs`: at most 16 concurrent FlowMux sessions per VM.
- I found no byte, bandwidth or total-transfer caps in the files I reviewed. Per-stream credit windows go up to 4 MiB (`limits.rs MAX_STREAM_CREDIT`). The theoretical worst-case credit memory is about 17 GiB (`MAX_FLOW_CREDIT_BYTES`).
- Protocols:
  - TCP: yes.
  - UDP: only under an unrestricted policy or an explicit UDP rule. An allowlist refuses `UDP ASSOCIATE` (`egress_gate.rs:496-503`, `flowmux.rs:762-777`).
  - DNS: only through the host and only for pinned names.
  - ICMP: mediated echo to allowlisted hosts (`egress_gate.rs:542-577`).
  - Raw IP: no.

## 6. Security posture

### Changes to guest-to-host attack surface when egress is enabled
1. **A new host process parses hostile input.** That process is `mvm-network-endpoint`, which reads FlowMux frames, DNS wire format, HTTP heads, and TLS when terminating. **On macOS it is unconfined:**
```rust
// crates/mvm-hostd/src/bin/mvm-network-endpoint.rs:568-578
/// macOS/Windows: no kernel LSM. ... we no-op so the bin (and its tests) build and run.
/// Production endpoints only ever run on Linux.
fn confine_endpoint_without_lsm(cfg: &EndpointConfig) -> Result<()> { let _ = resolver_uds_path(cfg); Ok(()) }
```
   It runs as your user and holds secrets in the clear if any are bound. ADR-039 (a root network helper on macOS) was rejected, so no privileged helper exists.
2. The host makes outbound connections and DNS lookups on the guest's behalf, but only to pinned addresses. It also uses the host's own `HTTPS_PROXY` if one is set.
3. vsock: the agent channel already exists. Egress adds port 5253 traffic, which goes through the same in-process virtio-vsock model.

### Advisories
`gh api repos/tinylabscom/mvm/security-advisories` lists four, all affecting **<= 0.24.2 with no patched version**, so v0.22.0 is affected:
- **GHSA-x85r-49ww-2pxq** (medium): guest-driven host memory growth in the virtio-vsock device model (`crates/mvm-vmm/src/vmm/vsock_transport.rs`). Transmit-gather with no cap, and an unbounded `pending_rx` queue. This is a host DoS. It exists even without egress (the agent uses vsock), but egress adds more vsock activity.
- GHSA-gvc3-rgqv-m9qj (high): externally signed plans can be replayed. Plans signed by the host's own key are not affected.
- GHSA-xjhp-hr84-rmcm (high): the GPU endpoint passes raw pointers. Only relevant with `--gpu`.
- GHSA-7pc3-7vgg-jqxr (high): `/tmp` socket dir and sudo chown, on Firecracker/Linux only.

### Relevant issues and changelog entries
- #3962: the released v0.22.0 on Linux/Firecracker failed every egress handshake because of guest/host FlowMux version skew (guest agentd 0.18.3). That was on Linux. The HVF smoke passes when both sides are built from the same tree (#3929/#3933). **Confirm that a single `--allow-host` run works on this host before you depend on it.**
- Fixes that landed after v0.22.0 and so are missing from it:
  - "Run the egress client as its own identity on the initramfs path" (0.24.0). In 0.22.0 the egress client may share the workload's uid, so the workload could kill it, replace it, or read its FlowMux key. This doesn't widen the policy, because the host still gates.
  - "Require signed audit for endpoint route decisions" (0.23.0).
  - "Stop crediting a FlowMux stream after resetting it" (0.23.0).
  - "Confine every thread of the network endpoint" (Linux-only).
  - #4829 (open): a per-host access log is still undecided.

### Inherent limits
- An allowlisted, write-capable API is an exfil channel, whatever the transport does. `--net`'s `dev` preset includes github.com, api.github.com, api.openai.com and api.anthropic.com.
- Because SNI and Host aren't checked, a hostname allowlist works as an IP allowlist.

## 7. Changing on a running machine

- The gate is built once per endpoint process (`network_endpoint.rs:46-57`), and docs `working/network.md:38-39` say ingress can't change after boot either.
- `machine reconfigure NAME [--net|--no-net] [--allow-host H ...|--clear-allow-host]` rewrites the spec. If the machine is running, it **stops and restarts** it (`crates/mvm-cli/src/commands/machine/spec_ops.rs:234-279`; flags at `machine/mod.rs:951-970`). There is no live update.
- `--peer`, `--grants-file` and `--policy` are only taken by `create` and `start` (`machine/mod.rs:697-736`, `start_create_flags.rs`).

## Recommendations

1. Use `--allow-host` with exact `host:443` entries. Avoid `--net`, which adds write-capable endpoints. Never use `--peer`.
2. Prefer destinations with dedicated IPs. Treat any CDN-fronted host as admitting its co-tenants.
3. Watch for `host.flow.*` and `dns.*` events by `vm_name` in `~/.mvm/audit/local.jsonl` and verify the chain. Expect no live rate limiting, so add your own watchdog on flow counts.
4. Because the endpoint has no sandbox on macOS, consider running the launcher, and therefore the endpoint, under a dedicated low-privilege macOS user, or wrapping it in `sandbox-exec` yourself. Enable egress only for runs that need it.
5. Make sure the host config has no `default_grants` egress and no `HTTPS_PROXY` you don't intend. Re-resolve by restarting machines that run longer than 24 h.
6. Before relying on egress, confirm with one `--allow-host` test that the FlowMux handshake succeeds on this host (#3962 skew).
